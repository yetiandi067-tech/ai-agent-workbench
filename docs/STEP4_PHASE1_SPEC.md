## 一、阶段目标

在现有架构上增加最小可用的主管 Agent 调度层，让用户可以提交一个目标任务，主管 Agent 将其拆解为多个子任务，分配给当前可执行的 Mock Agent，按依赖顺序执行，跟踪状态，并汇总结果。

**本阶段只实现 Mock 调度链路，不调用任何真实大模型。**

## 三、主管 Agent 的职责

新增一个主管调度服务，复用已有架构，不要再造一套平行系统。

主管服务需要支持：

- 接收用户输入的总目标。
- 生成结构化的任务计划。
- 将总目标拆分成多个有明确输入、输出和验收标准的子任务。
- 给子任务指定 Agent、依赖关系和执行顺序。
- 只有依赖全部成功的子任务才能执行。
- 依赖失败时，阻止后续依赖任务并标记原因。
- 汇总子任务结果，生成总任务报告。
- 对每个子任务保留状态、执行记录、输出和错误信息。

## 四、任务规划方式

本阶段不使用大模型生成计划。实现确定性的 Mock Planner，保证测试可重复。

至少支持以下任务类型：

1. `research`：模拟资料收集。
2. `analysis`：模拟分析。
3. `writing`：模拟生成文本。
4. `review`：模拟检查和修改建议。

对于用户输入的目标，Mock Planner 生成一个合理的默认计划，至少包含两个子任务，并体现依赖关系。例如：

- `research`：收集任务所需的基础信息。
- `analysis`：依赖 `research`，根据上一步结果进行分析。
- `writing`：依赖 `analysis`，生成阶段性成果。
- `review`：依赖 `writing`，检查成果并给出结论。

可以依据关键词决定是否省略某些阶段，但必须保证计划结构清晰、可预测且易于测试。不得假装 Mock 结果是真实研究、真实模型推理或外部事实。

每个子任务至少包含：

- 稳定的任务 ID。
- 所属总任务 ID。
- 标题与任务说明。
- 任务类型。
- 输入与预期输出说明。
- 验收标准。
- 指定 Agent ID。
- 依赖任务 ID 列表。
- 状态与时间戳。
- 执行结果或错误信息。

## 五、调度与执行规则

1. 复用现有 TaskRunner、状态机、事件记录和 SQLite 持久化。
2. 增加必要的总任务与子任务关联关系；优先扩展现有数据结构，避免重复建表或重复实现状态机。
3. 如果现有数据库 schema 需要变更，使用新的版本化迁移，保留已有数据，禁止删除数据库重建。
4. 调度器每次只选择依赖均已成功的可执行子任务。
5. 子任务失败后，不得继续执行依赖该任务的下游任务。
6. 不自动重试，不创建无限循环，不自动反复规划。
7. 不允许多个调度器重复执行同一个子任务。
8. 任务执行顺序、状态变化和失败原因必须能从事件记录中追溯。
9. 如果取消、超时和状态恢复能力已有实现，应复用并测试；不要在本阶段重新设计一套机制。
10. 总任务完成条件必须明确：所有必要子任务成功才算成功；失败或被阻断时，总任务应体现失败或部分完成，不得谎报成功。

## 六、UI 要求

在现有界面基础上增量实现主管调度入口。优先扩展任务中心，不重做整个 UI。

用户至少能够：

1. 输入一个总目标。
2. 预览主管 Agent 生成的 Mock 计划。
3. 查看每个子任务的标题、Agent、依赖关系和验收标准。
4. 明确点击后开始执行整个 Mock 计划。
5. 查看每个子任务的实时状态和结果。
6. 查看最终汇总报告和失败原因。

界面必须清晰标识“Mock 演示结果”，不能让用户误以为是真实模型生成的内容。

不需要本阶段新增复杂可视化。优先确保交互闭环和错误反馈。

## 七、安全与边界

- 不调用真实 DSH，不调用其他真实 Agent。
- 不读取、输出或修改任何密钥、令牌或账号凭据。
- 不修改 `cordis.patch.yml`、DSH 安装目录、其他 Agent 配置或系统环境变量。
- 不增加自动重试、后台自动调用、并发压力测试或自动执行用户未确认的计划。
- 不新增未验证的外部 API。
- 不删除现有数据库、任务记录、日志或会话文件。
- 不安装不必要的依赖；优先使用现有技术栈。
- 保留真实模型调用的现有默认关闭、双重确认和并发限制。
- 不改变已有 Mock/DSH Adapter 的行为，除非有必要且有测试证明兼容。
- 如发现架构障碍，先采用最小兼容方案并记录，不要借机重构整个项目。

## 八、测试要求

至少补充自动化测试，覆盖：

1. Mock Planner 生成有效且可重复的计划。
2. 子任务依赖顺序正确。
3. 依赖任务未成功时，下游任务不能执行。
4. 子任务失败后，依赖它的任务被阻断。
5. 全部子任务成功时，总任务正确完成并生成汇总报告。
6. 部分失败时，总任务不能被错误标记为成功。
7. 子任务状态和事件记录正确。
8. 数据库迁移兼容已有数据。
9. 不调用真实模型即可完成整条 Mock 流程。
10. 现有测试继续通过。

测试必须使用 Mock 或临时数据库，不得发起真实模型调用。

## 九、分阶段实施顺序

按以下顺序执行：

A. 检查现有代码和 Git 基线，提交实施计划。

B. 设计最小数据结构和接口，先完成 Mock Planner 与依赖调度的单元测试。

C. 实现主管调度服务，复用现有任务执行、事件和持久化能力。

D. 实现 IPC/Preload/Renderer 接入，完成 UI 交互闭环。

E. 运行全部测试、类型检查和构建；修复本阶段引入的问题。

F. 检查 Git diff，确认没有误改 DSH 配置、密钥文件、用户数据或无关模块。

不要提前开始第 5 步，不要接入真实主管大模型。

## 十、验收标准

只有满足以下条件才算阶段 1 完成：

- 可以输入总目标并预览结构化计划。
- 可以明确确认后执行 Mock 计划。
- 子任务按依赖顺序执行。
- 失败时下游任务正确阻断。
- 最终报告与实际子任务结果一致。
- 总任务、子任务、运行记录和事件能够持久化。
- 重启后仍能查看历史执行记录。
- UI 清楚标识 Mock 结果。
- 真实模型调用次数为 0。
- `npm run typecheck`、`npm run test`、`npm run build` 全部通过。
- 不破坏第 3 步已验收的安全护栏。
- 提交完整的实施报告，包括修改文件、数据库迁移、测试结果、Git diff 摘要、未解决问题和实际验证边界。

完成后停止，等待下一条指令。不要自动继续下一阶段。

## 用户将重点核对的六项

1. 调度是否真实存在，而不只是 UI 展示一份预设计划。
2. 子任务是否通过现有 Adapter 实际执行 Mock，而不是直接伪造成功状态。
3. 依赖失败后是否确实阻断下游任务。
4. 数据库迁移是否保留第 3 步的数据。
5. 是否误触发 DSH 真实调用，或破坏已有安全护栏。
6. 测试是否覆盖真实调度逻辑，而不只是测试几个独立函数。

注意：这一阶段只做主管调度层的 Mock 版本。等这条链路通过验收后，再制定阶段 2 的提示词，接入真实 DSH 执行能力。
