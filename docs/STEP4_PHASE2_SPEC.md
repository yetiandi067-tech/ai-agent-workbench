## 三、核心任务 A：人工可执行的 Mock 端到端验收

启动桌面应用，不执行任何真实模型调用。逐项验证：

1. 应用正常启动，页面无致命错误。
2. 任务中心能输入总目标。
3. 点击生成计划后出现计划预览。
4. 预览显示子任务标题、类型、依赖关系、执行 Agent、验收标准。
5. 未点「确认执行」前不自动执行任何子任务。
6. 确认后 Mock 子任务按依赖顺序执行。
7. 能查看各子任务状态、执行结果、错误信息。
8. 计划结束后能查看汇总报告。
9. 刷新/重启后历史计划及子任务状态仍在。
10. 页面明确显示「Mock 演示结果」。

优先用已有 UI 验证。当前执行环境不能真实 GUI 操作时必须如实说明，给出可亲自操作的逐步验收清单，**不得把自动化单元测试当作 GUI 验收**。

## 四、核心任务 B：依赖调度与失败阻断专项检查

1. 只有所有依赖均为 `succeeded` 时才能执行该子任务。
2. 上游失败/超时/取消后，所有下游依赖任务都必须被阻断。
3. 阻断递归传播到更下游，不能遗留永远 `pending` 的子任务。
4. 被阻断子任务必须有 `BLOCKED_BY_DEPENDENCY` 错误码与可读阻断原因。
5. 计划完成时不允许仍有 `pending`/`running` 子任务。
6. 全部成功 → `succeeded`。
7. 有成功也有失败/阻断 → `partial`。
8. 零成功且失败 → `failed`。
9. 重复点击确认 / 重复 IPC / 同时两次确认，不得导致同一计划子任务重复执行。
10. 循环依赖、无效依赖 ID、依赖缺失等异常计划应拒绝执行或明确失败，不能无限循环。

**特别检查 `confirmPlan` 是否在第一次 `await` 前同步建立防重复执行保护。** 若两个请求可能同时通过 `status === 'draft'` 检查，必须增加可靠的进程内运行锁或等效保护，并编写并发测试。

检查状态更新是否统一复用现有状态机。**禁止直接改数据库状态绕过合法转换**；若确需特殊恢复路径，必须记录原因并测试。

## 五、核心任务 C：重启恢复与持久化

1. 计划执行中退出，重启后不得自动继续执行未知状态任务。
2. 正在运行的真实任务仍遵循现有 `needs_confirmation` 恢复策略。
3. 计划与子任务状态必须一致，不能出现「计划已完成、子任务仍在跑」。
4. 恢复时明确显示「上次运行被中断，需要人工检查」，不得把未知结果伪装成失败或成功。
5. 历史计划、子任务关联、依赖列表、汇总报告可读取。
6. schema v1 → v2 迁移可重复启动，旧任务数据保留。

不删除/重建/清空现有数据库。迁移测试使用独立临时数据库。

## 六、核心任务 D：计划汇总报告

审查报告是否真实依据数据库最终子任务状态生成，至少包含：总目标、计划状态、子任务总数、成功/失败/阻断数量、每个子任务名称/类型/最终状态、失败或阻断原因、各子任务结果摘要、计划完成时间、明确的「Mock 演示结果」标识。

不能把未执行任务伪装成成功，不能把空结果当有效产出。统计口径不一致则修复并加测试。

## 七、核心任务 E：测试补齐

1. 计划创建只生成草稿，不执行任务。
2. 正常依赖链按顺序执行。
3. 第一项任务失败，全部下游被阻断。
4. 中间任务失败，后续任务递归阻断。
5. 上游超时或取消时，依赖阻断行为正确。
6. 计划最终状态与子任务统计一致。
7. 重复确认不会重复执行。
8. 并发确认不会重复执行。
9. 无效依赖和循环依赖能被拒绝或安全终止。
10. 完成计划不存在遗留 `pending`/`running` 子任务。
11. 重启恢复不会自动重跑不确定任务。
12. 汇总报告与数据库最终状态一致。
13. v1 → v2 迁移保留旧数据。
14. 页面或 IPC 层对无效目标、无效计划 ID、非法状态转换有明确错误处理。

测试必须可重复、确定性强，不依赖真实模型、网络或真实 API 密钥。

- 删除用户数据库、清理历史任务或执行破坏性 Git 操作。
- 大范围重构无关模块。
- 引入主管 Agent 自主循环或真实多 Agent 路由。

现有真实调用安全护栏必须保持不变。
